# AirDrop somente com o AIC 8800D80 / AirDrop using only the AIC 8800D80

## Português

**Estado:** pesquisa; nenhum suporte AirDrop foi implementado. A release v1.1.2 permanece inalterada.

No Mac de teste, o AIC enumera como `a69c:8d81`, mas não há `IO80211Interface` nem `awdl0`. O Wi-Fi atual usa um serviço próprio e uma interface de rede UTUN; isso fornece acesso à rede, não o enlace direto de que o AirDrop precisa. O [modelo de segurança da Apple](https://support.apple.com/en-ie/guide/security/sec2261183f4/web) descreve descoberta por Bluetooth LE e comunicação por Wi-Fi peer-to-peer.

O [driver Linux do AIC](https://github.com/radxa-pkg/aic8800/blob/main/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_main.c) contém caminhos P2P. Isso sugere uma capacidade a investigar, **não prova compatibilidade com AWDL**, nem que a revisão/firmware deste dongle permita associação STA e AirDrop simultâneos. Projetos de driver Wi-Fi nativo para outros chips também relatam dificuldade com AWDL ([exemplo: OpenIntelWireless](https://github.com/OpenIntelWireless/itlwm/issues/292)).

**Medição no dongle de teste (19/10/2026):** `lmac_version=06090101`, `features=01e877d7`, `max_stations=32`, `max_interfaces=4`. Pela enumeração `mm_features` da [revisão do driver AIC fixada neste projeto](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/lmac_msg.h), estão ligados `MM_FEAT_MROLE_BIT` (4), `MM_FEAT_P2P_BIT` (13) e `MM_FEAT_P2P_GO_BIT` (14); `MM_FEAT_CHNL_CTXT_BIT` (11) está desligado. Esses bits isoladamente não provam criação de interface P2P, concorrência STA/P2P ou AWDL; os testes físicos posteriores confirmaram criação de VIF e recepção de candidatos AWDL, mas não um enlace funcional.

O [NetworkingDriverKit público da Apple](https://developer.apple.com/documentation/networkingdriverkit) oferece somente interface Ethernet; a [orientação da Apple para Wi-Fi](https://developer.apple.com/documentation/driverkit/creating-a-driver-using-the-driverkit-sdk) aponta para uma extensão de kernel. Portanto, criar `en0` com DriverKit não faria o macOS tratar o AIC como AirPort nem habilitaria AirDrop. A SDK instalada não contém cabeçalhos públicos IO80211; a integração Wi-Fi nativa exige pesquisa de API privada e validação cuidadosa em uma EFI de testes.

**Direção do protótipo nativo (sem instalação):** O macOS 15.8.1 desta máquina contém o pacote `IO80211Family.kext`, mas `kmutil showloaded` não o lista, `ioreg` não encontra `IO80211Interface` e `ifconfig` não mostra `awdl0`. A SDK local não expõe cabeçalhos públicos de `IO80211Controller`. Como referência arquitetural, o [AirportItlwm](https://github.com/OpenIntelWireless/itlwm/blob/master/AirportItlwm/AirportItlwm.hpp) implementa `IO80211Controller`, interface virtual, saída de quadros 802.11 e operações AWDL; isso demonstra a amplitude da integração, **não compatibilidade do AIC nem AirDrop funcional**. A pesquisa deve construir um controlador AIC próprio para a ABI do Sequoia, mantendo o USB com um único dono e transportando eventos de gerenciamento, estado do rádio e dados entre o controlador e o serviço. A hipótese de começar com um controlador virtual que converse com o serviço existente ainda precisa de teste de carregamento e ciclo de vida; nenhum kext instalável foi produzido ou instalado. A ponte atual em `wifi/native_backend.py` só entrega quadros Ethernet e não implementa esse contrato Wi-Fi/AWDL. Primeiro gate real: carregar o protótipo **apenas em EFI de teste**, observar `IO80211Interface` ligada ao AIC e verificar que o Wi-Fi estável pode ser restaurado. `awdl0` e, depois, uma transferência AirDrop bidirecional são gates separados.

`native/AICAirPortController.cpp` é um **esqueleto original para a ABI experimental do Sequoia**; seu `start()` recusa registrar uma interface fantasma sem ponte de rádio. `native/AICNativeBridgeUserClient.cpp` acrescenta apenas uma porta de controle restrita a administrador, com consulta de versão de ABI, sem comando de rádio; como o controlador não inicia, essa porta ainda não pode ser aberta. O primeiro cabeçalho `IO80211Controller` (Sonoma) compilava, mas a auditoria encontrou dezenas de símbolos não exportados nas coleções locais: **não era um alvo válido de carregamento**. O script agora usa, fora deste repositório, os cabeçalhos `macOS15/IO80211ControllerV2.h` do [fork itlwm para Sequoia](https://github.com/laobamac/itlwm/tree/738d4c61b5a64433b27c1ab09dba94916ab77d8d) e o [MacKernelSDK](https://github.com/acidanthera/MacKernelSDK/tree/3f750085caa17ec3a7880f11c11bf4f48cd6a164). Nenhum cabeçalho de terceiros foi copiado para o AIC. Com esse par de referências, `tools/check_native_controller.sh` compilou dois objetos x86_64, ligou um Mach-O `kext bundle` com *dynamic lookup* e encontrou os 526 símbolos externos solicitados nas coleções de kernel desta máquina. **Presença de símbolo não comprova layout de classe, ABI, dependências declaradas, carregamento ou funcionamento.** O [próprio fork](https://github.com/laobamac/itlwm/blob/main/README.md) ainda declara AWDL/AirDrop sem suporte, mesmo com Wi-Fi nativo; portanto esse gate não resolve o objetivo sozinho. Antes de habilitar `start()`, faltam transporte real de comandos/eventos kernel–serviço, registro Skywalk/IO80211, callbacks STA/AWDL, proprietário único do USB, empacotamento e rollback em EFI de teste.

Marcos técnicos, nesta ordem:

1. Medir, sem derrubar a conexão estável, versão, bits de capacidade e número de interfaces virtuais informados pelo firmware. A branch experimental já grava apenas esses quatro valores quando o serviço normalmente inicia; `tools/airdrop_preflight.py` os mostra quando disponíveis. Ainda será necessário medir suporte a quadros de gerenciamento/ação e alternância de canal. Separar o que o driver Linux implementa do que este firmware realmente confirma.
2. Prototipar **fora da EFI de uso diário** uma interface Wi-Fi nativa do macOS para o AIC. O código atual de `native_backend.py` referencia uma ponte nativa, mas o pacote 1.1.2 a mantém desativada e não inclui um driver IO80211/AWDL funcional.
3. Fazer a interface peer-to-peer trocar quadros reais com outro dispositivo Apple, mantendo a conexão à rede. A presença de `awdl0` é apenas um indicador intermediário, não prova AirDrop.
4. Testar descoberta, envio e recebimento de arquivos, reconexão Wi-Fi, Bluetooth e dois reinícios consecutivos antes de falar em suporte.

Use `python3 tools/airdrop_preflight.py` para verificar apenas os sinais locais de interface e enumeração USB. A saída não inclui SSID, MAC ou senha. O campo `airdrop_proven` ficará falso até existir um teste de transferência real; o script não habilita AirDrop.

Para consultar o firmware **instalado agora**, execute `sudo sh tools/probe_firmware_identity.sh` no Terminal a partir da raiz deste repositório. Isso interrompe o Wi-Fi AIC por alguns segundos e tenta religar o serviço mesmo em caso de falha. A saída útil contém somente `lmac_version`, `features`, `max_stations` e `max_interfaces`. Não execute durante trabalho que dependa da conexão; se a reconexão falhar, reinicie o Mac com sua EFI de recuperação disponível.

**Teste físico de VIFs (19/10/2026):** `tools/probe_p2p_vif.sh` criou uma interface STA e uma P2P no firmware e confirmou índices distintos. Removeu ambas, reiniciou o serviço AIC; a consulta posterior ao controle do serviço retornou `ok=true`, `enabled=true`, `dongle_present=true` e `connected=true`. O dongle continuou enumerado como `a69c:8d81`. Isso não testa tráfego simultâneo, permanência em canal ou transmissão de quadros P2P e não habilita AirDrop. A máquina continuou sem `IO80211Interface` e sem `awdl0` após o teste.

O [caminho RX do driver AIC](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_rx.c) separa quadros de gerenciamento dos dados Ethernet usando `flags_is_80211_mpdu` no [cabeçalho RX](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_rx.h). O parser experimental `wifi/management.py` reconheceu quadros de ação em lotes USB reais no teste passivo abaixo, mas ainda não foi ligado ao serviço. O mesmo módulo codifica o pedido `MM_REMAIN_ON_CHANNEL_REQ`, já aceito no teste físico isolado. O [caminho Linux de TX de gerenciamento](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_tx.c) usa `TXU_CNTRL_MGMT`, fila VO e estação desconhecida (`0xff`). Esta branch agora codifica esse descritor apenas para quadros de ação 802.11 não protegidos e valida seu formato na biblioteca USB experimental; os testes offline passaram, mas **nenhum quadro de ação foi transmitido pelo dongle**. A biblioteca instalada continua sem esse caminho. Ainda faltam teste físico de TX/RX com outro aparelho, concorrência com STA conectado, driver Wi-Fi nativo e AWDL.

**Teste físico ROC (19/10/2026):** `tools/probe_roc.sh` compilou uma biblioteca USB experimental num diretório temporário, pausou o serviço AIC, abriu VIFs STA e P2P, pediu 200 ms no canal 44 (5220 MHz) e recebeu confirmação de aceitação e indicação de término. A biblioteca e os arquivos instalados não foram substituídos. Após a limpeza e reativação do serviço, o controle informou `ok=true`, `enabled=true`, `dongle_present=true`, `connected=true`. As VIFs deste teste não estavam associadas a uma rede durante o ROC; portanto ele **não comprova** operação simultânea STA conectada + P2P, transmissão de quadros de ação, AWDL ou AirDrop.

**Captura passiva inicial (19/10/2026):** Com o AirDrop aberto em outro aparelho Apple e autorização do usuário, `tools/probe_roc.sh --capture` repetiu a criação das VIFs e ouviu por 1 segundo no canal 44. ROC foi aceito e expirou normalmente, mas o parser recebeu `rx_batches=0`, `action_frames=0`, `awdl_candidates=0`. A conexão AIC voltou (`connected=true`). O teste não transmitiu quadros nem guardou MACs, nomes ou pacotes. **Correção metodológica posterior:** essa versão chamava `Wifi.data_read()`, que descarta lotes USB que não se encaixam no parser Ethernet. Portanto `rx_batches=0` não comprova que o endpoint USB ficou sem tráfego. O classificador usa apenas o prefixo de ação específico AWDL publicado no [código-fonte OWL](https://github.com/seemoo-lab/owl/blob/master/src/frame.h); uma correspondência futura ainda não provaria um enlace funcional.

**Repetição inicial em três canais (19/10/2026):** Com nova autorização e o AirDrop aberto, a captura passiva ouviu 1 segundo por canal em 6, 44 e 149, os três canais citados pelo [OWL](https://github.com/seemoo-lab/owl/blob/master/README.md). As três VIFs P2P foram criadas em sequência; as três solicitações ROC foram aceitas e expiraram. O parser retornou `rx_batches=0` em cada canal, sem quadros de ação ou candidatos AWDL; o serviço voltou conectado. **Esse zero está comprometido pelo descarte de lotes em `Wifi.data_read()`**, então não diferencia canal errado, filtro do firmware ou parser. Os testes posteriores com a fila USB bruta estão descritos abaixo. No [driver AIC desta revisão](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_main.c), o callback `mgmt_frame_register` está vazio e não aparece nas operações `cfg80211`; portanto não há indicação de uma etapa de registro dinâmico omitida pelo teste.

**Controle de monitor (19/10/2026):** Com autorização separada, o primeiro experimento temporário criou uma VIF de monitor, mas abortou **antes** de escutar quadros. A causa do timeout foi um erro nosso: o script enviou `0x1412` (identificador da confirmação) como se fosse `ME_CONFIG_MONITOR_REQ`; pela [enumeração do driver AIC](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/lmac_msg.h), o pedido correto é `0x1411` e a confirmação é `0x1412`. Portanto o timeout **não é evidência contra o firmware**. O código e os testes foram corrigidos e repetidos fisicamente, conforme o resultado abaixo. A limpeza removeu a VIF, reiniciou o rádio e reativou o serviço; a consulta posterior retornou `ok=true`, `enabled=true`, `dongle_present=true`, `connected=true`. A revisão do [driver Linux](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/Makefile) usa `CONFIG_RWNX_TL4=n`, `CONFIG_RWNX_MON_RXFILTER=n` e `CONFIG_RWNX_MON_DATA=n` por padrão.

**Controle de monitor corrigido (19/10/2026):** Após nova autorização, o firmware confirmou `ME_CONFIG_MONITOR_REQ` correto para o canal 44 e a escuta de 3 segundos recebeu `usb_batches=5491`. O parser reconheceu `bounded_records=2479` e `beacons=40`; não conseguiu interpretar `unparsed_batches=3012`, possivelmente por formatos ou alinhamento diferentes, portanto os totais de tipos de quadro são limites inferiores, não um inventário completo. Nenhum quadro de ação ou candidato AWDL foi reconhecido nessa janela; não foi confirmado se o outro aparelho estava anunciando AirDrop. A VIF temporária foi removida e o serviço voltou com `connected=true`. Isso é um controle positivo de recepção USB em **monitor**, não prova de RX em P2P, concorrência STA+monitor, AWDL ou AirDrop. O bit `MM_FEAT_MON_DATA_BIT` não está presente nas capacidades medidas do dongle, e a configuração de referência do driver mantém `CONFIG_RWNX_MON_DATA=n`; não presumir monitor simultâneo com Wi‑Fi conectado.

**P2P com USB bruto (19/10/2026):** Após corrigir a captura para ler a fila USB diretamente, uma nova repetição autorizada com AirDrop aberto ouviu os canais 6, 44 e 149 por 1 segundo cada. As três janelas ROC foram aceitas e expiraram, mas o endpoint de dados entregou `rx_batches=0` em cada uma. O serviço voltou conectado. Agora o zero **não é artefato do parser Ethernet**, embora ainda possa refletir filtro de BSSID, ausência de quadros naquele intervalo ou outra condição da VIF P2P.

**P2P com filtro de outro BSSID (19/10/2026):** Com nova autorização e AirDrop aberto no outro aparelho, `tools/probe_roc.sh --capture-filtered` repetiu a escuta de 1 segundo em cada canal. O pedido `MM_SET_FILTER_REQ` foi aceito; as três VIFs P2P foram criadas, e todos os pedidos ROC foram aceitos e expiraram. O endpoint USB entregou respectivamente **9, 8 e 9 lotes** nos canais 6, 44 e 149. O parser reconheceu **9 quadros de ação no canal 6 e 5 no canal 149**; todos os 14 corresponderam ao prefixo de ação específico AWDL definido no [OWL](https://github.com/seemoo-lab/owl/blob/master/src/frame.h). Não houve lotes malformados. O filtro segue o [pedido de referência AIC](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_msg_tx.c) com bits de [`reg_access.h`](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/reg_access.h), sem habilitar dados arbitrários de outras redes. Este resultado demonstra recepção de **candidatos AWDL** enquanto a VIF P2P e o ROC estavam ativos; a contagem não preservou o índice de VIF indicado em cada cabeçalho RX, portanto ainda não atribui os quadros especificamente à VIF P2P. Também não autentica o emissor, não demonstra resposta do AIC, enlace AWDL ou AirDrop. A captura não transmitiu nem salvou pacotes, MACs ou nomes. O serviço voltou com `ok=true`, `enabled=true`, `dongle_present=true`, `connected=true`.

**Atribuição de VIF (19/10/2026):** Uma repetição autorizada da mesma captura, com AirDrop aberto, recebeu 11 candidatos no canal 6 e 6 no canal 149. Todos os 17 tinham `flags_vif_idx=255`; as VIFs criadas eram STA `0` e P2P `1`. O serviço voltou conectado. A [revisão fixada do driver AIC](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_defs.h) define `RWNX_INVALID_VIF=0xff`, e o [caminho RX de gerenciamento](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_rx.c) encaminha quadros sem VIF indicada para todas as VIFs ativas. Assim, `255` **não identifica a VIF P2P nem indica falha de recepção**; uma futura implementação precisa rotear esses quadros explicitamente. O teste não provou TX, sincronização AWDL, `awdl0` ou AirDrop.

**Checagem do comprimento AWDL (19/10/2026):** As contagens anteriores exigiam apenas o prefixo público, a posição do subtipo e um mínimo de 31 bytes. Com outra autorização e AirDrop aberto, a sonda `awdl_complete_headers` repetiu a escuta e encontrou **15 de 15 candidatos no canal 6** e **19 de 19 no canal 149** com ao menos 40 bytes: comprimento suficiente para o [cabeçalho 802.11 de 24 bytes e o cabeçalho AWDL fixo de 16 bytes descrito pelo OWL](https://github.com/seemoo-lab/owl/blob/master/src/frame.h). Todos ainda tinham `flags_vif_idx=255`; no canal 44 não houve candidatos. O serviço voltou com `ok=true`, `enabled=true`, `dongle_present=true`, `connected=true`. A checagem confirma **comprimento e prefixo**, mas não valida os demais campos fixos, TLVs, emissor ou enlace. O backend `native_backend.py` atualmente transporta Ethernet para uma ponte experimental; ele não fornece interface AWDL nativa.

**Preparação de TX, ainda sem transmissão física:** O encoder e o validador USB experimentais agora aceitam somente quadros de ação pública (`4`) ou vendor-specific não protegida (`127`). O [driver AIC de referência](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_tx.c) ajusta o bit de gerenciamento robusto conforme a categoria; a [regra do kernel Linux](https://github.com/torvalds/linux/blob/master/include/linux/ieee80211.h) exclui essas duas categorias do tratamento robusto. Outras categorias são rejeitadas em vez de serem enviadas com descritor incorreto. O script `tools/probe_roc.sh --tx-check` foi preparado para enviar **um** quadro público de diagnóstico no canal 6, sem payload AWDL, e restaurar o serviço, mas **não foi executado**; exige autorização separada porque interrompe brevemente o Wi-Fi e emite RF. Isso foi verificado apenas por testes locais; o dongle ainda não transmitiu um quadro de ação neste projeto. O foco principal agora é a interface nativa, não repetir testes de rádio sem uma pergunta concreta.

**Regra de segurança:** não instalar um kext experimental na EFI principal nem desativar proteções do macOS para “forçar” AirDrop. Usar uma EFI de teste com backup e possibilidade de rollback.

## English

**Status:** research only; AirDrop support has not been implemented. Release v1.1.2 is unchanged.

On the test Mac, the AIC enumerates as `a69c:8d81`, but neither `IO80211Interface` nor `awdl0` is present. The current Wi-Fi uses a custom service and a UTUN network interface; it provides network access, not the direct link AirDrop needs. [Apple's security documentation](https://support.apple.com/en-ie/guide/security/sec2261183f4/web) describes Bluetooth LE discovery and peer-to-peer Wi-Fi communication.

The [AIC Linux driver](https://github.com/radxa-pkg/aic8800/blob/main/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_main.c) contains P2P paths. This suggests a capability worth investigating, **not proven AWDL compatibility** or simultaneous STA/AirDrop operation on this dongle revision and firmware. Native Wi-Fi drivers for other chips have also encountered AWDL difficulties ([OpenIntelWireless example](https://github.com/OpenIntelWireless/itlwm/issues/292)).

**Measurement on the test dongle (2026-10-19):** `lmac_version=06090101`, `features=01e877d7`, `max_stations=32`, `max_interfaces=4`. According to `mm_features` in the [AIC driver revision pinned by this project](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/lmac_msg.h), `MM_FEAT_MROLE_BIT` (4), `MM_FEAT_P2P_BIT` (13), and `MM_FEAT_P2P_GO_BIT` (14) are set; `MM_FEAT_CHNL_CTXT_BIT` (11) is clear. These bits alone do not prove P2P VIF creation, concurrent STA/P2P operation, or AWDL; later physical tests confirmed VIF creation and reception of AWDL candidates, but not a working link.

Apple's public [NetworkingDriverKit](https://developer.apple.com/documentation/networkingdriverkit) supports Ethernet interfaces only; [Apple's Wi-Fi driver guidance](https://developer.apple.com/documentation/driverkit/creating-a-driver-using-the-driverkit-sdk) points to a kernel extension. Creating `en0` with DriverKit would therefore not make the AIC appear as an AirPort device or enable AirDrop. The installed SDK has no public IO80211 headers; native Wi-Fi integration requires private-API research and careful validation using a test EFI.

**Native prototype direction (not installed):** This machine's macOS 15.8.1 contains the `IO80211Family.kext` bundle, but `kmutil showloaded` does not list it, `ioreg` finds no `IO80211Interface`, and `ifconfig` shows no `awdl0`. The local SDK exposes no public `IO80211Controller` headers. As an architectural reference, [AirportItlwm](https://github.com/OpenIntelWireless/itlwm/blob/master/AirportItlwm/AirportItlwm.hpp) implements `IO80211Controller`, virtual interfaces, raw 802.11 output, and AWDL operations; that illustrates the integration scope, **not AIC compatibility or working AirDrop**. Research must build an AIC-specific controller for the Sequoia ABI, keep a single USB owner, and carry management events, radio state, and data between the controller and the service. Starting with a virtual controller that talks to the existing service is a hypothesis requiring load/lifecycle testing; no installable kext has been produced or installed. The existing `wifi/native_backend.py` bridge delivers Ethernet frames only and does not fulfill this Wi-Fi/AWDL contract. The first real gate is to load the prototype **only with a test EFI**, observe an AIC-backed `IO80211Interface`, and verify that stable Wi-Fi can be restored. `awdl0` and then a bidirectional AirDrop transfer are separate gates.

`native/AICAirPortController.cpp` is an **original skeleton for the experimental Sequoia ABI**; its `start()` refuses to register a ghost interface without a radio bridge. `native/AICNativeBridgeUserClient.cpp` adds only an administrator-restricted control endpoint with an ABI-version query and no radio commands; because the controller refuses to start, this endpoint cannot yet be opened. The first (Sonoma) `IO80211Controller` header compiled, but a symbol audit found dozens of names not exported by the local kernel collections: **that was not a viable load target**. The script now uses the [Sequoia itlwm fork](https://github.com/laobamac/itlwm/tree/738d4c61b5a64433b27c1ab09dba94916ab77d8d) `macOS15/IO80211ControllerV2.h` headers and [MacKernelSDK](https://github.com/acidanthera/MacKernelSDK/tree/3f750085caa17ec3a7880f11c11bf4f48cd6a164), both kept outside this repository. No third-party headers were copied into AIC. With those references, `tools/check_native_controller.sh` compiled two x86_64 objects, permissively linked a Mach-O `kext bundle` using dynamic lookup, and found all 526 requested external symbols in this Mac's kernel collections. **Symbol presence does not prove class layout, ABI, declared dependencies, loading, or operation.** The [fork itself](https://github.com/laobamac/itlwm/blob/main/README.md) still lists AWDL/AirDrop as unsupported despite native Wi-Fi, so this gate alone does not satisfy the objective. Before enabling `start()`, work remains on actual kernel–service command/event transport, Skywalk/IO80211 registration, STA/AWDL callbacks, single USB ownership, packaging, and test-EFI rollback.

Engineering gates, in order:

1. Without interrupting the stable connection, record the firmware version, feature bits, and virtual interface count. The experimental branch now records only these four values when the service starts normally; `tools/airdrop_preflight.py` displays them when available. Management/action-frame support and channel switching still need investigation. Distinguish Linux-driver code paths from capabilities confirmed by this firmware.
2. Prototype an AIC-backed macOS native Wi-Fi interface **outside the daily-boot EFI**. The current `native_backend.py` references a native bridge, but package 1.1.2 disables it and includes no functioning IO80211/AWDL driver.
3. Exchange actual peer-to-peer frames with another Apple device while preserving infrastructure Wi-Fi. The presence of `awdl0` is only an intermediate signal, not proof of AirDrop.
4. Test discovery, file sending and receiving, Wi-Fi reconnection, Bluetooth, and two consecutive reboots before claiming support.

Run `python3 tools/airdrop_preflight.py` to check local interface and USB-enumeration signals only. Its output excludes SSIDs, MAC addresses, and passwords. `airdrop_proven` remains false until a real transfer test exists; this script does not enable AirDrop.

To query the firmware **currently installed**, run `sudo sh tools/probe_firmware_identity.sh` in Terminal from this repository's root. This briefly interrupts AIC Wi-Fi and attempts to restart its service even if the query fails. The useful output contains only `lmac_version`, `features`, `max_stations`, and `max_interfaces`. Do not run it during connection-critical work; if reconnection fails, restart the Mac with your recovery EFI available.

**Initial passive capture (2026-10-19):** With AirDrop open on another Apple device and user approval, `tools/probe_roc.sh --capture` recreated the VIFs and listened for one second on channel 44. **Initial three-channel repeat (2026-10-19):** With fresh approval and AirDrop open, passive capture listened for one second each on channels 6, 44, and 149, the three channels listed by [OWL](https://github.com/seemoo-lab/owl/blob/master/README.md). The three successive P2P VIFs were created, and all three ROC requests were accepted and expired. The parser returned `rx_batches=0` on each channel, with no action frames or AWDL candidates; the service reconnected. **These zeroes are confounded by `Wifi.data_read()` discarding batches**, so they do not distinguish wrong channel, firmware filtering, or parser behavior. Later raw-USB queue tests are described below. In [this AIC driver revision](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_main.c), `mgmt_frame_register` is empty and absent from `cfg80211_ops`, so there is no apparent omitted dynamic registration step.

**Monitor control (2026-10-19):** With separate approval, the first temporary probe created a monitor VIF but aborted **before** listening. The timeout was our error: the script sent `0x1412` (the confirmation ID) as `ME_CONFIG_MONITOR_REQ`. The [AIC driver enum](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/lmac_msg.h) assigns `0x1411` to the request and `0x1412` to the confirmation. Thus the timeout is **not evidence against firmware support**. Code and tests were corrected and physically repeated, as described below. Cleanup removed the VIF, reset the radio, and restarted the service; a later query returned `ok=true`, `enabled=true`, `dongle_present=true`, `connected=true`. The reference [Linux driver](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/Makefile) defaults to `CONFIG_RWNX_TL4=n`, `CONFIG_RWNX_MON_RXFILTER=n`, and `CONFIG_RWNX_MON_DATA=n`.

The parser recognized `bounded_records=2479` and `beacons=40`; it could not interpret `unparsed_batches=3012`, possibly due to different formats or alignment, so frame-type totals are lower bounds, not a full inventory. **VIF attribution (2026-10-19):** A separately approved repeat of the same capture, with AirDrop open, received 11 candidates on channel 6 and 6 on channel 149. All 17 had `flags_vif_idx=255`; the created VIFs were STA `0` and P2P `1`. The service reconnected. The [pinned AIC driver](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_defs.h) defines `RWNX_INVALID_VIF=0xff`, and its [management RX path](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_rx.c) forwards frames without an assigned VIF to all active VIFs. Thus `255` **neither identifies the P2P VIF nor signals failed reception**; a future implementation must route these frames explicitly. The test did not prove TX, AWDL synchronization, `awdl0`, or AirDrop.

**AWDL length check (2026-10-19):** Earlier counts required only the public prefix, subtype offset, and a minimum of 31 bytes. With separate approval and AirDrop open, the `awdl_complete_headers` probe repeated the listen and found **15 of 15 candidates on channel 6** and **19 of 19 on channel 149** with at least 40 bytes: enough for the [24-byte 802.11 header and 16-byte fixed AWDL header described by OWL](https://github.com/seemoo-lab/owl/blob/master/src/frame.h). All still had `flags_vif_idx=255`; channel 44 had no candidates. Service status returned to `ok=true`, `enabled=true`, `dongle_present=true`, `connected=true`. This check confirms **length and prefix**, but does not validate the remaining fixed fields, TLVs, sender, or link. The existing `native_backend.py` transports Ethernet to an experimental bridge; it does not provide a native AWDL interface.

**TX preparation, no physical transmission yet:** The experimental encoder and USB validator now accept only public (`4`) or unprotected vendor-specific (`127`) action frames. The [AIC reference driver](https://github.com/radxa-pkg/aic8800/blob/e9e43ed/src/USB/driver_fw/drivers/aic8800/aic8800_fdrv/rwnx_tx.c) sets the robust-management bit according to category; the [Linux kernel rule](https://github.com/torvalds/linux/blob/master/include/linux/ieee80211.h) excludes these two categories from robust handling. Other categories are rejected rather than sent with the wrong descriptor. `tools/probe_roc.sh --tx-check` has been prepared to send **one** non-AWDL public diagnostic action on channel 6 and restore the service, but **has not been run**; it requires separate approval because it briefly interrupts Wi-Fi and emits RF. This is only locally tested; this project has not transmitted an action frame through the dongle. The primary focus is now the native interface, not further radio tests without a concrete question.

**Safety rule:** do not install an experimental kext into the primary EFI or disable macOS protections to “force” AirDrop. Use a test EFI with backup and rollback available.
